# Agentic AI Evaluation Harness

## Explicit warning

> **These results come from entirely synthetic data.** The queries, labels, departments and
> knowledge passages in `backend/evaluations/dataset.json` are invented fixtures. They are
> **NOT real university queries, NOT real university performance, and NOT real-world model
> accuracy.** Never quote these metrics as a measure of how well the system performs at a real
> university.

The harness evaluates the existing bounded LangGraph workflow in `backend/app/agents`
(classification → routing → knowledge_research → response_drafting → validation). It is
test infrastructure only: no production application code is changed, and no database writes
leave the in-memory SQLite database created per run.

## Files

| Path | Purpose |
| --- | --- |
| `backend/evaluations/dataset.json` | Versioned synthetic dataset (24 labelled queries). |
| `backend/evaluations/evaluate.py` | CLI and metric computation. |
| `backend/tests/test_agent_evaluation.py` | Deterministic offline tests. |
| `backend/eval_reports/evaluation.json` | Default JSON report (generated by running the evaluator). |
| `backend/eval_reports/evaluation.md` | Default Markdown report (generated by running the evaluator). |

## Running the offline evaluation (default, no network)

Run from `backend/`:

```powershell
.\.venv\Scripts\python.exe -m evaluations.evaluate `
  --output-json eval_reports/evaluation.json `
  --output-md eval_reports/evaluation.md `
  --model-version offline-label-echo-v1
```

Offline mode is the default. It replaces the LLM with `LabelEchoLlm`, a deterministic fake
whose outputs are derived only from dataset labels. It opens no network connection, creates
no OpenAI client, uses no randomness, and reports token usage/cost as `null`. The high label
accuracies therefore verify **pipeline wiring and metric computation**, not model quality.

To use the dataset bundled with the package, omit `--dataset`. To evaluate a different
synthetic dataset, add:

```powershell
  --dataset evaluations/dataset.json
```

## Running the tests

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_agent_evaluation.py
```

The tests validate the dataset schema, run the offline evaluator into temporary directories,
assert that report counts match the dataset size, verify that version metadata and the
synthetic-data caveat appear in both formats, check abstention handling, and confirm that a
live client is never constructed (including a negative test that live mode refuses to run
without a key).

These tests need no database fixtures or network access; they run with the standard shared
`tests/conftest.py` as shown above.

## Running the live evaluation (opt-in, requires a key)

```powershell
.\.venv\Scripts\python.exe -m evaluations.evaluate `
  --live `
  --model-version gpt-4o-mini `
  --output-json eval_reports/live_evaluation.json `
  --output-md eval_reports/live_evaluation.md
```

Live mode is only entered when `--live` is passed explicitly. It reads `OPENAI_API_KEY` from
`backend/.env` (or the environment), constructs the **official OpenAI SDK** client with
`max_retries=0`, and calls the model configured by `OPENAI_MODEL`. If `--model-version` is
provided in live mode it also sets the model used for the calls, so the report label matches
the model that was actually invoked. If no key is available the command fails with a clear
error; it never silently falls back to the fake. **Live calls may incur real API cost** even
though the dataset is synthetic.

## CLI arguments

| Flag | Default | Meaning |
| --- | --- | --- |
| `--live` | off | Opt in to real OpenAI calls. Requires `OPENAI_API_KEY`. |
| `--model-version` | `offline-label-echo-v1` offline; `OPENAI_MODEL` live | Version label recorded in the report. |
| `--output-json` | `backend/eval_reports/evaluation.json` | JSON report path. |
| `--output-md` | `backend/eval_reports/evaluation.md` | Markdown report path. |
| `--dataset` | `backend/evaluations/dataset.json` | Dataset JSON path. |

## Dataset and versioning

- `dataset_version` is stored in `dataset.json` and copied verbatim into both reports.
- `model_version` comes from `--model-version` (or the offline/live default) and is copied
  into both reports alongside `mode`, `generated_at` and the dataset description.
- Bump `dataset_version` whenever records, labels or expected sources change. Always pass a
  meaningful `--model-version` so runs can be compared.
- Records are validated strictly (no extra fields): `id`, `topic`, `query`, `expected_intent`,
  `expected_category`, `expected_priority`, `expected_department`,
  `expected_department_keyword`, `expected_sources`, `expected_abstention`,
  `expected_unsupported_claim` and `entities`. Ids must be unique and at least 20 records are
  required.
- The synthetic approved corpus lives in `evaluate.py` (`_SYNTHETIC_KNOWLEDGE`); its source
  ids are the only valid `expected_sources`. The corpus is likewise synthetic.

## Metric definitions

All values are computed from the workflow's actual final state for each record and then
aggregated; none are hard-coded.

| Metric | Definition |
| --- | --- |
| Intent classification accuracy | Fraction of records where `classification.intent` equals `expected_intent`. |
| Category classification accuracy | Fraction where `classification.category` equals `expected_category`. |
| Priority prediction accuracy | Fraction where `priority_recommendation` equals `expected_priority`. |
| Department routing accuracy | Fraction where the routed department name equals `expected_department` (case-insensitive) or contains `expected_department_keyword`. |
| Knowledge retrieval precision | Micro-average: correct retrieved source ids ÷ all retrieved ids. Empty retrieval scores 1.0 for that record. |
| Knowledge retrieval recall | Micro-average: correct retrieved source ids ÷ expected source ids. Empty expectation scores 1.0. |
| Citation correctness | Fraction where every cited id (draft `source_ids` plus inline `[id]` references) is in the retrieved approved source set. |
| Unsupported claim count | Number of records whose **final** draft still contains a fabricated id or one of the harness's synthetic unsupported phrases. Four records are labelled `expected_unsupported_claim: true` to exercise the guardrail. |
| Abstention correctness | Fraction where the retrieval node's `no_evidence` decision equals `expected_abstention`. |
| Latency | Wall-clock time per workflow invocation; reported as mean/p95/min/max in ms and explicitly labelled **synthetic-run latency** (offline) or live-run latency on a small synthetic set. Not production latency. |
| Token usage / estimated cost | Summed from provider usage metadata when available; `null` in offline mode. Cost is always `null` because no verified price table is bundled. |

## Limitations

- Offline labels are echoed by the fake LLM, so classification/routing accuracies of 1.0 are
  expected and say nothing about real model performance.
- Retrieval uses a small synthetic keyword corpus, so precision reflects invented token
  overlap, not production retrieval quality.
- The dataset is small (24 records) and deliberately unbalanced across topics; it is a smoke
  test for the harness and the guardrails, not a statistically meaningful benchmark.
- Offline latency measures local graph/database overhead only; live latency is dominated by
  network and provider conditions and is not a production SLA measurement.
- The harness does not modify or configure the production knowledge repository, prompts or
  validation rules.
- **Above all: synthetic results must never be presented as real university performance or
  real-world accuracy.**
